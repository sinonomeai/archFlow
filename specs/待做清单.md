### P0 执行路线（按可演示里程碑）

| 阶段 | 目标 | 包含事项 | 出口（能演示什么） |
| --- | --- | --- | --- |
| S0 契约 | 先把会返工的结构定死 | P0-01、P0-13、P0-10 的 pino 部分、P0-11 骨架 | 类型编译通过；图 / 中断结构有 Zod 与单测；日志带 traceId |
| S1 账号与骨架 | AC1 | P0-14、P0-15、P0-02 收尾 | 注册→登录→空态引导→建项目→建会话→刷新仍在 |
| S2 画布 | AC4 | P0-16 | 拖拽→3 秒保存→刷新还原；双标签 409 不覆盖 |
| S3 Agent | AC2 / AC3 | P0-09、P0-03、P0-04、P0-05、P0-06、P0-07 | 发消息→流式文字→卡片→回答→图渲染到画布 |
| S4 沉淀 | AC5 / AC6 | P0-18 | 保存资产→侧栏出现；恢复快照；fork 隔离 |
| S5 知识 | AC7 | P0-17、P0-08 | 上传 md→提问→引用来源 |
| S6 收口 | 可交付 | P0-19、P0-12、P1-02 / P1-03 / P1-08 / P1-09 | mock 删除；测试 / 限流 / 评测达标 |

**为什么这么排**

- 业务 CRUD 必须早于 Agent：run 挂在 conversation / message 上，没有真实会话就只能用脚本测 Agent，无法端到端验收。原清单把 Agent 放在第三步，会把这个缺口留到最后。
- 图契约必须早于 Agent 图生成和画布：否则 Agent、画布、资产各写一套节点结构，返工三次。
- 画布早于 Agent：AC4 可以先用固定图验证拖拽与保存，Agent 生成图后直接复用同一条链路。
- 每个阶段都对应一条验收标准，避免“做了很多但演示不了”。

**并行建议**

- 两人时：S1 的后端 CRUD 与前端登录 / 引导页可以并行；S2 前端画布与 S3 后端 Agent 可以并行，前提是 P0-13 已定稿。
- 不建议并行改 `packages/shared`：契约文件一次只让一个人动，避免互相覆盖。

**第一批 PR 建议**

1. `feat(shared,db): 补齐运行中断与图契约`（P0-01 + P0-13）
2. `feat(api): 系统接口、pino 与测试骨架`（P0-02 收尾 + P0-10 前半 + P0-11）
3. `feat(api): 认证全链路`（P0-14）

## 6. 明确不在清单内

以下事项属于 MVP 红线或已明确不做，不要因为“架构完整”而提前实现：

- PDF / DOCX 解析（post-MVP 才由 Go 服务承担）。
- BullMQ / Redis 队列；MVP 不做 RabbitMQ，post-MVP 统一用 RabbitMQ。
- 完整微服务拆分、服务网格、API Gateway。
- WebSocket / Yjs 多人协作。
- LangChain / LangGraph / Vercel AI SDK。
- MCP、reasoner、rerank、混合检索在 MVP 中落地。
- Skill 插件市场、多 Agent 编排、Skill 全局可变开关。
- BYOK / 自定义 Base URL；当前只考虑平台预设模型，不与 P2-10 混做。
- 密码重置（forgot / reset）：接口定义保留，MVP 不实现，前端不接入。
- 画布节点内容编辑 / 增删连线 / 数据流可视化：MVP 只要求渲染、拖拽、缩放、Dagre 自动布局；编辑能力见 P2-15 / P2-16。

## 8. 完成定义

一项任务标记 `✅` 前，至少满足：

1. 契约先改 `packages/shared`，类型检查通过；涉及数据库的补迁移。
2. 有对应测试或可复现的验收步骤（写清命令），不能只写“已实现”。
3. 错误路径有明确返回码，不泄露堆栈 / SQL / 内部路径。
4. 关键路径有 traceId 和日志。
5. 文档中的契约与代码一致；行为变了就同步 `API文档` / `表设计` / `数据流`。
6. 前端功能必须走真 API；在 P0-19 完成前，mock 只能作为开发脚手架，不能作为验收证据。
