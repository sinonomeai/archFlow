### 接口

```http
GET /api/v1/conversations/:conversationId/layout
PUT /api/v1/conversations/:conversationId/layout
```

PUT 请求：

```json
{ "layout": { "nodes": { "n1": { "x": 120, "y": 80 } } }, "baseVersion": 0 }
```

- `baseVersion` 不一致返回 `409 DRAFT_VERSION_CONFLICT`，`data.currentVersion` 给服务端最新版本；
- 首次保存 `baseVersion = 0`，成功后版本从 1 开始；
- 自动布局会忽略旧坐标，按 Dagre 重排并保存新布局；
- 手工拖拽节点在 `onNodeDragStop` 时保存，刷新后按 `layout_data` 还原。

# 设计思考

## 难点一：约束提取与提示词编排

- 分析原因：大模型对提示词首尾部分的记忆力更准确。为提供Agent输出的准确率与召回率，

- 初步方案：把聊天记录（`messages`）全量拉取出来，每次都拼在 Prompt 里发给大模型。

- 推翻过程：全量发送会导致 Token 爆炸、成本剧增，而且历史废话会干扰当前推理。如果只存文本，大模型还得去文本里提取约束，导致LLM幻觉。

- 最终决定：

    1. 提取约束：抽离出独立的 `agent_states` 表，把约束存为结构化 JSONB（`constraints_data`），且给 `conversation_id` 加 Unique 约束（只保留最新状态）。

    2. 上下文截断：只拼接最近的10条（根据指标调整）消息

    3. RAG匹配：将RAG匹配字段拼接与末尾，用户消息之前

## 难点二：画布高频拖拽与版本回退

- 分析原因：用户拖拽 React Flow 画布是极高频率的操作。如果每次拖拽都直接写数据库，数据库 IO 会被打满；依赖用户手动保存不仅影响体验，一旦遇到意外情况还可能导致草稿丢失。

- 初步方案：给画布建一个历史版本表，每次用户拖拽或者 AI 生成图，都插入一条新记录。

- 推翻过程：画布 JSON 极大，高频插入会导致数据库体积迅速膨胀。且用户存在无效操作，产生冗余数据，增加存储开销。

- 最终决定：采用“草稿覆盖 \+ 快照分离”。`conversations` 表只存一个 `current_draft_graph`（覆盖更新），配合前端做 3 秒防抖（Debounce）静默保存。真正的历史版本，只通过 `messages` 表里的 `graph_snapshot` 字段来记录。只存 AI 生成图的关键节点，不存用户的无意义拖拽。

## 难点三：多分支对话与上下文污染

- 分析原因：用户经常想“回到过去的某句话，重新开个话题”。如果在同一会话里改，会污染当前的聊天上下文，右侧画布状态也会发生错乱。

- 初步方案：像 Git 一样，在 `messages` 表里加 `parent_id`，建一个复杂的树状结构，前端做分支切换器。

- 推翻过程：树状结构的查询和渲染极其复杂，前端要写大量递归代码。且如果用户删除老会话，新分支如果没有做物理隔离，会导致数据残缺。最关键的是，对话分支了但画布没分支，依然会精神污染。

- 最终决定：抛弃树状指针，采用“物理复制”（Fork）。当用户点击某条消息“开启新对话”时，后端直接新建一个会话，把该消息及之前的历史原封不动拷贝到新会话里。同时，把该消息的 `graph_snapshot` 赋给新会话的草稿。保证新老会话数据绝对隔离，查询永远是单线查询。

## 难点四：混合交互（UI 卡片\+纯文本）与结构化提取

- 分析原因：AI 聊天往往只能纯文本问答，但架构助手需要让用户做选择题（如“团队几人？”），还要能应对用户选择直接编辑约束。如果只有纯 `TEXT` 字段，前端无法渲染复杂的交互 UI，大模型也极难从几十轮的自由文本里精准提取出结构化的参数。

- 初步方案：在数据库里单独建一张 `constraint_cards` 表，专门用来存卡片的 ID、选项、用户的选择状态，以及它属于哪条消息。

- 推翻过程：引入新表会导致严重的“状态同步灾难”。如果用户不点卡片，而是直接打字说“改成 5 人”，这张表的状态就没人更新，会产生脏数据；而且前后端要同时维护 `messages` 和 `constraint_cards` 两张表，查询和渲染成本剧增。

- 最终决定：
  放弃建新表，直接在 `messages` 表引入 `metadata` \(JSONB\) 字段。把所有交互形态统统塞进消息体里：

    1. 前端渲染：`metadata.card` 存 `ConstraintCard`（`{ id, kind, title, options, status, answer, ... }`），前端看到 `card` 就渲染单选 / 多选 / 输入 UI，而不是普通气泡。

    2. Agent 提取：当用户点击选项或直接打字时，后端通过原生 Function Calling（工具调用）让大模型输出 JSON（如 `{ teamSize: "5人" }`），然后更新到难点一的 `agent_states` 表中。

---

## 其他：

1. 双主键设计（内部 `id BIGINT` 自增 \+ 外部 `uuid`）：自增 id 仅库内使用（JOIN、索引、级联），**任何响应都不暴露**；对外一律用 `id` 字段，值为 `uuid`，映射在 Nest 序列化层（DTO / 拦截器）统一完成。既保住 B\+ 树顺序插入性能，又避免暴露自增序列。

1. 双 token 认证（NestJS \+ Redis）：access token 短效、由前端内存持有；refresh token 的 hash 与 TTL 存于 Redis，按用户/设备族维护，检测到复用即整族吊销并返回 `REFRESH_INVALID`。数据库**不建 token 表**。
