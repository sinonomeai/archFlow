# 5\. Agent

## 本地工作台

仅在 `apps/web/.env.local` 中设置 `MOCK_API=1` 时，Web 工作台以 `/api/mock` 运行同源的消息与 SSE 演示。默认由固定响应模拟阶段、文字和图；再设置 `ARCHFLOW_PREVIEW_AGENT=1` 可选模型驱动。默认工作台走正式 `/api/v1`。 [启动方式](../../README.md#隔离的本地预览)

| Mock 入口 | 用途 |
| --- | --- |
| `POST /api/mock/conversations/:conversationId/messages` | 带 `Idempotency-Key` 受理消息，返回 `202` 和运行句柄。卡片作答使用同一路径，并带 `interruptId` |
| `GET /api/mock/conversations/:conversationId/messages` | 获取最近消息。加载更早的消息时沿 `nextCursor` 往前翻页 |
| `GET /api/mock/conversations/:conversationId/run` | 查询活跃任务和最近任务，供切回会话或刷新页面时接回 |
| `GET /api/mock/runs/:runId/stream` | 带 Bearer 订阅 SSE。重连带最后应用的 `Last-Event-ID` |
| `GET /api/mock/runs/:runId` | 获取持久化任务与其助手消息，在 SSE 不可用时轮询 |
| `POST /api/mock/runs/:runId/cancel` | 请求取消。已保存的草稿继续可用 |

本地任务和分段保存的文字按账号写入文件。只断开订阅时，后台任务继续执行。缓冲覆盖游标时补发后续帧。缓冲不可用时发送携带 `run`、`assistantMessage` 和 `stage` 的 `snapshot` 帧，客户端用其替换已显示的运行视图。历史架构图取自对应助手消息的 `graphSnapshot`，当前画布读会话的最新草稿。Web 服务重启后，被打断的活跃任务在读取时标记失败，未过期的待回答问题可继续作答。

选择「用这张图提问」后，客户端随消息发送可选的 `graphReferenceMessageId`。服务端从当前账号、当前会话的助手消息读取图。引用不可用时返回 `404 MESSAGE_NOT_FOUND`。用户也可以在澄清时补选历史图，沿用原任务。所选历史图供解释使用，草稿继续由当前会话的画布管理。带引用的改图请求提示移除引用后重新发送。

### 5.0 统一会话入口与传输

从本节起定义正式 `/api/v1` 契约。上游原有鉴权和 SSE 已接线；新增编排服务尚未替换正式运行入口，整合进度见 [待做清单](../待做清单.md)。

客户端提交用户内容、可选附件和幂等键。正式入口目前使用原有的约束收集与图生成流程。先检查等待澄清、再按意图路由并选择直接执行或制定计划属于待整合的新编排；请求契约仍以 `SendMessageInput` 为准。编排目标与状态归属见 [架构规划](../架构规划.md#10-agent-编排架构)。

| 方法与路径 | 作用 |
| --- | --- |
| `POST /conversations/:conversationId/messages` | 受理任务或恢复等待中的任务，返回 `202` 和运行句柄 |
| `GET /runs/:runId/stream` | 用 `Last-Event-ID` 订阅、重连或续传 |
| `GET /runs/:runId` | 查询运行状态，为流断线提供查询入口 |
| `POST /runs/:runId/cancel` | 请求取消运行 |

前端使用 `@microsoft/fetch-event-source`，在请求头带 `Authorization` 和适用的 `Last-Event-ID`。重复请求使用同一个 `Idempotency-Key`。SSE 连接断开后，服务端继续执行。数据库保留运行和消息，事件缓冲用于逐帧重放。



### 5\.1 发送消息（受理）



```HTTP
POST /api/v1/conversations/:conversationId/messages
Idempotency-Key: <uuid>
```



**请求体**：



```JSON
{
  "content": "帮我设计订单服务的架构",
  "attachments": ["fil_1", "fil_2"]
}
```



|字段|必填|约束|
|---|---|---|
|`content`|是|长度见 `SendMessageInput`（服务端先 trim 再计长）|
|`attachments`|否|文件 ID 数组，约束见 `SendMessageInput`。运行层校验项目归属，资料检索仅使用 `ready` 文件。附件上传和选择见 P0-17。|



> **注意**：**不再接收 ****`currentGraph`**。服务端一律以会话的 `draftGraph` 为准（单一数据源，消除 P0\-3 竞态）。
> 
> 若前端有未保存的图，先 `PUT /draft` 成功后再发消息，顺序由前端保证。
> 
> 



**响应 ****`202 Accepted`**：



```JSON
{
  "runId": "run_9f1c",
  "userMessageId": "msg_49",
  "assistantMessageId": "msg_50",
  "streamUrl": "/api/v1/runs/run_9f1c/stream",
  "status": "queued"
}
```

> 新任务受理后的 `queued` 表示尚未开始。SSE 的 `run-start`、`status` 或 `GET /runs/:runId` 提供之后的状态。等待输入时按本节恢复既有运行。
>
> `streamUrl` **由服务端按 `runId` 生成**（`runStreamUrl(runId)`，见 Zod `agent.schema.ts`）；前端必须原样请求，不得自行拼接前缀。
> 
> 



**错误**：



|HTTP|code|说明|
|---|---|---|
|409|`CONVERSATION_BUSY`|会话忙，`data.activeRunId` 让前端**接回**已有流，而不是丢弃|
|422|`MESSAGE_TOO_LONG`|消息过长|
|404|`CONVERSATION_NOT_FOUND`|会话不存在|



### 5\.2 获取流（SSE）



```HTTP
GET /api/v1/runs/:runId/stream
Authorization: Bearer <accessToken>
Last-Event-ID: 12        ← 可选，断线重连时带上
```



**响应头（必须全部设置）**：



```HTTP
Content-Type: text/event-stream; charset=utf-8
Cache-Control: no-cache, no-transform
Connection: keep-alive
X-Accel-Buffering: no
```



> `X-Accel-Buffering: no` 缺了的话，Nginx 会把整个流缓冲到结束才吐 —— 这是 SSE 最常见的「明明后端在流、前端一片空白」的元凶。
> 
> 



**帧格式**：



```Plain Text
id: 12
data: {"type":"text-delta","messageId":"msg_50","content":"建议"}
```



- 每帧**必须有 ****`id:`**（每个 run 内从 1 开始递增；`Last-Event-ID` 只在同一 `runId` 下有义），否则 `Last-Event-ID` 续传无从谈起。

- `data:` 后面是一个完整 JSON 对象（**单行**，不含换行）。

- 帧间用**空行**分隔。

    

**心跳**：无业务输出时，每 **15 秒**发一次注释帧，防止网关空闲超时：



```Plain Text
: ping
```



**流内事件表**：



|`type`|字段|说明|
|---|---|---|
|`run-start`|`runId`, `conversationId`, `userMessageId`, `assistantMessageId`, `traceId`, `resume?`|**首帧，必须有**。前端靠它把流和消息绑定；`resume: true` 表示从 HITL 断点续流，前端保留已有气泡，不清空本地文本|
|`status`|`stage`: 见 `RunStage`|`thinking` / `searching_knowledge` / `drafting_graph` / `finalizing`|
|`text-delta`|`messageId`, `content`, `replace?`|增量文本由前端追加。`replace: true` 时用 `content` 整体替换本地气泡，适用于合成重放或重试过程中修正已显示的文字|
|`citation`|`sources[]`: `{fileId, fileName, snippet, score}`|知识库引用|
|`graph`|`graph`（`Graph`）, `replace: true`|已校验并提交的全量图。画布版本冲突时保留当前草稿，并报告 `DRAFT_VERSION_CONFLICT`|
|`constraint-card`|`messageId`, `card`（`ConstraintCard`，含 `id`）|见 §6|
|`card-updated`|`cardId`, `status`, `answer`|可选，多卡片场景用|
|`interrupt`|`interruptId`, `kind`, `node`, `payload`, `expiresAt`|HITL 暂停帧；收到后关闭当前流，**不发送终态 `done`**；用户输入后 resume 同一 run|
|`usage`|`inputTokens`, `outputTokens`, `model`, `latencyMs`|仅观测|
|`title`|`conversationId`, `title`|流内可用的会话标题，前端可更新侧边栏。异步完成后的权威标题从会话详情或项目树读取|
|`error`|`code`, `message`, `retryable`|流内错误，**之后仍要发 ****`done`**** \+ ****`[DONE]`**|
|`done`|`assistantMessageId`, `finishReason`|终态结束发送，携带终态信息；HITL 暂停不发 `done`，改发 `interrupt`|



**结束标志**：



```Plain Text
data: {"type":"done","assistantMessageId":"msg_50","finishReason":"stop"}
data: [DONE]
```



> `done` 携带元信息，`[DONE]` 是终止哨兵（兼容前端既有解析逻辑）。收到任一即停止解析，并**重新拉一次 ****`GET /conversations/:id/messages`** 拿服务端权威数据。
>
> HITL 暂停是例外：只发 `interrupt`，不发 `done` / `[DONE]`；恢复后重新建立流。
> 
> 

标题与推荐问题在主回答提交后独立调度。后续读取消息可获得 `metadata.suggestedQuestions`，后续读取会话或项目树可获得标题。主流照常结束。辅助生成失败不改变主任务的完成状态。



**重连规则**：



|情况|行为|
|---|---|
|带有效 `Last-Event-ID` 重连|**优先**从该 id 的**下一帧**开始补发；补发完继续实时推送。不重复发送之前的帧|
|未带 `Last-Event-ID`，run 仍在运行|把缓冲内已有的帧全部补发，之后继续实时推送|
|run 已结束且在缓冲期内（10 分钟）|完整重放全部帧，然后发 `done` \+ `[DONE]` 并关闭|
|run 处于 `waiting_input`|从 `runs.metadata.interrupt` 重放 `interrupt` 帧后关闭；**不返回 409**，也不发 `done`|
|缓冲已失效（超期 / 进程重启）|**不返回 409**：按 `runId` 查 `runs` → `messages`，合成快照重放（见下）|
|`Last-Event-ID` 大于当前缓冲最新帧|服务重启 / 缓冲重建导致旧游标失效：忽略旧游标，按全量重放；不要因此返回 409|
|run 存在但关联的 assistant 消息已缺失|`409` / `RUN_NOT_RESUMABLE`，前端刷新消息列表|
|run 不存在 / 不属于当前用户|`404` / `RUN_NOT_FOUND`|

#### 事件缓冲与恢复（实现约束）

- **断线不终止运行**：`GET /runs/:runId/stream` 断开只关闭推送通道，不触发取消。Agent 继续推理，继续写事件缓冲和 `messages.content`。只有 `POST /runs/:runId/cancel`、运行超时、进程退出会终止 run。
- **数据库是权威存储**：生成过程中，服务端把累积文本按节流（约 1 秒或每 200 token，取先到者）写入 `messages.content`；终态再最终写入 `content`、`metadata.citations`、`metadata.usage`，并更新 `runs.status` / `finish_reason` / `usage` / `finished_at`。所以缓冲丢失后，`GET /messages` 仍能拿到已生成内容。
- **事件缓冲只用于逐帧重放**：MVP 单实例放进程内存（`Map<runId, { frames, lastId, expiresAt }>`），TTL 10 分钟，不引入 Redis。缓冲不是权威数据，进程重启即丢失。
- **缓冲失效的合成重放**：服务端按 `runs.assistant_message_id` 取对应消息，依次发送 `run-start`、来自 `messages.content` 的全量 `text-delta`（`replace: true`）、该消息保存的架构图快照（如有）以及适用的终态 `done` 和 `[DONE]`。卡片、引用与用量从该消息的 `metadata` 和 `runs` 补齐。当前画布独立读会话的 `current_draft_graph`。
- **缓冲生命周期**：run 进入终态后保留 10 分钟，到期清理；服务重启时清空。
- **全量补发时重置气泡**：未带 `Last-Event-ID` 或缓冲失效重放时，`run-start` 到达后前端应清空对应 assistant 气泡的本地累积文本，再按后续帧重建，避免重复追加；合成重放的 `text-delta` 本身带 `replace: true`，可幂等覆盖。续答时保留此前已完成的气泡，并按 `assistantMessageId` 处理新的助手消息。



#### HITL 中断与恢复（interrupt / waiting_input）

1. 引擎需要用户澄清时返回检查点和问题。运行层把当前 `Interrupt` 与检查点写入 `runs.metadata`，把 `runs.status` 置为 `waiting_input`，发送 `interrupt` 帧后关闭当前 SSE 流。
2. `Interrupt` 包含 `interruptId`、`kind`、`node`、`payload`、`expiresAt`。当前执行器使用 `clarification`，`approval` 和 `review` 为后续必须答复的交互保留。
3. 用户恢复：
   - 卡片作答走 `POST /api/v1/conversations/:conversationId/messages/:messageId/answer`；
   - 当前会话等待输入时，普通消息可提交澄清答案。服务端将答案记为独立的用户消息，并继续原 run；
   - 恢复按 `interruptId` 幂等。引擎使用原请求、检查点和答案继续。
4. 上游正式 `RunService` 恢复时保留原 `runId`，但会创建一条新的助手消息并更新 `assistantMessageId`，使时间线呈现“用户答复 → 助手继续”。新编排预览复用原助手消息。正式新编排接入时须统一两者的消息契约并同步前端。续答 `run-start` 带 `resume: true`。
5. 等待超时（建议 24 小时）转 `canceled`；用户也可调用 `POST /api/v1/runs/:runId/cancel` 显式取消。
6. 如果客户端在 `waiting_input` 期间重连 `GET /stream`，服务端从 `runs.metadata.interrupt` 重放 `interrupt` 帧后关闭，不返回 `409`。

### 5.3 查询运行状态（轮询兜底）





```HTTP
GET /api/v1/runs/:runId
```



**响应 ****`200 OK`**：



```JSON
{
  "id": "run_9f1c",
  "conversationId": "cnv_1",
  "userMessageId": "msg_49",
  "assistantMessageId": "msg_50",
  "status": "succeeded",
  "finishReason": "stop",
  "createdAt": "2026-11-08T16:40:00+08:00",
  "finishedAt": "2026-11-08T16:40:09+08:00",
  "error": null
}
```



`error` 非空时：`{ ``"code": "INTERNAL_ERROR"``, "message": "..." }`



> **用途**：SSE 被企业代理缓冲/截断时的兜底。前端可退化为「1\.5s 轮询一次，`status` 变为终态后再拉消息列表」。
> 
> 



### 5\.4 取消生成



```HTTP
POST /api/v1/runs/:runId/cancel
```



**响应 ****`202 Accepted`**（取消是异步的，`status` 返回当前状态）：



```JSON
{ "runId": "run_9f1c", "status": "running" }
```



> 服务端尽快停止推理并保存已生成的部分内容。终态 `canceled` 和 `finishReason = canceled` 通过 SSE `done` 帧或 `GET /runs/:runId` 获得。
