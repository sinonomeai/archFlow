# 5\. Agent

### 5\.0 从「POST 直接返回 SSE」改成「POST 受理 \+ GET 取流」（还没让AI reAct，这个是我自己指定方向的修改方案）



**原设计的问题**：



1. **断线即失败**。网络抖动、切后台、用户锁屏，流断开后没有任何恢复手段，AI 吐了一半的内容直接丢了，用户只能重发。

2. **无法重试**。POST 重试会重新触发一次完整推理 —— 既烧钱又产生两条重复消息。

3. **无法取消**。用户发现方向错了想中断，没有接口，只能等它跑完继续烧 token。

4. **HTTP 200 \+ 流内错误**。一旦开流，HTTP 状态码就固定 200 了，后续错误只能塞进流里，监控和告警系统看不到。

5. **无法轮询兜底**。SSE 在某些企业代理 / 老网关下会被缓冲或截断，前端完全无解。

    

**新设计**：



```Plain Text
POST /conversations/:id/messages        → 202 + runId（受理，立即返回，毫秒级）
GET  /runs/:runId/stream                → SSE 取流（可重连、可续传）
GET  /runs/:runId                       → 查终态（轮询兜底）
POST /runs/:runId/cancel                → 取消
```



**收益**：



- `runId` 是稳定句柄 → 断线后 `GET /runs/:runId/stream` 重连，带 `Last-Event-ID` 续传

- `runId` \+ `Idempotency-Key` → 重试返回同一个 `runId`，绝不重复推理

- 有 `cancel` 接口 → 用户能中断

- 有 `GET /runs/:id` → SSE 被代理吃掉时，前端可轮询终态再刷新消息列表

- 服务端可保留事件缓冲 **10 分钟**（可配置），够覆盖绝大多数断线场景

    

> **重要提醒（必须让前端知道）**：即使改成了 GET，浏览器原生 `EventSource` **仍然无法携带 ****`Authorization`**** 头**（这是 EventSource 的规范限制，与 HTTP 方法无关）。所以前端统一使用 **`@microsoft/fetch-event-source`** 消费 SSE：它基于 `fetch`，可携带 `Authorization` / `Last-Event-ID`，并内置断线重试。**不手写 `ReadableStream` 解析，也不使用原生 `EventSource`。**
> 
> 
> 
> 另：**绝不允许把 AccessToken 直接放 query**（会进 access log）。选型见 `specs/DECISIONS.md` 第 14 条。
> 
> 



### 5\.1 发送消息（受理）



```HTTP
POST /api/v1/conversations/:conversationId/messages
Idempotency-Key: <uuid>
```



**请求体**：



```JSON
{
  "content": "帮我设计订单服务的架构",
  "attachments": ["fil_1", "fil_2"]
}
```



|字段|必填|约束|
|---|---|---|
|`content`|是|长度见 `SendMessageInput`（服务端先 trim 再计长）|
|`attachments`|否|文件 id 数组，条数见 `SendMessageInput`。服务端校验文件属于同一项目。**暂不实现**：v1\.2 仅保留字段定义，前端暂不上传附件|



> **注意**：**不再接收 ****`currentGraph`**。服务端一律以会话的 `draftGraph` 为准（单一数据源，消除 P0\-3 竞态）。
> 
> 若前端有未保存的图，先 `PUT /draft` 成功后再发消息，顺序由前端保证。
> 
> 



**响应 ****`202 Accepted`**：



```JSON
{
  "runId": "run_9f1c",
  "userMessageId": "msg_49",
  "assistantMessageId": "msg_50",
  "streamUrl": "/api/v1/runs/run_9f1c/stream",
  "status": "queued"
}
```

> `status` 返回 `queued`：受理即入队，尚未开始推理；开跑后由 SSE 的 `run-start` / `status` 帧推进，也可用 `GET /runs/:runId` 查最新态。前端不要把 202 的 `queued` 当成"正在生成"。
>
> `streamUrl` **由服务端按 `runId` 生成**（`runStreamUrl(runId)`，见 Zod `agent.schema.ts`）；前端必须原样请求，不得自行拼接前缀。
> 
> 



**错误**：



|HTTP|code|说明|
|---|---|---|
|409|`CONVERSATION_BUSY`|会话忙，`data.activeRunId` 让前端**接回**已有流，而不是丢弃|
|422|`MESSAGE_TOO_LONG`|消息过长|
|404|`CONVERSATION_NOT_FOUND`|会话不存在|



### 5\.2 获取流（SSE）



```HTTP
GET /api/v1/runs/:runId/stream
Authorization: Bearer <accessToken>
Last-Event-ID: 12        ← 可选，断线重连时带上
```



**响应头（必须全部设置）**：



```HTTP
Content-Type: text/event-stream; charset=utf-8
Cache-Control: no-cache, no-transform
Connection: keep-alive
X-Accel-Buffering: no
```



> `X-Accel-Buffering: no` 缺了的话，Nginx 会把整个流缓冲到结束才吐 —— 这是 SSE 最常见的「明明后端在流、前端一片空白」的元凶。
> 
> 



**帧格式**：



```Plain Text
id: 12
data: {"type":"text-delta","messageId":"msg_50","content":"建议"}
```



- 每帧**必须有 ****`id:`**（每个 run 内从 1 开始递增；`Last-Event-ID` 只在同一 `runId` 下有义），否则 `Last-Event-ID` 续传无从谈起。

- `data:` 后面是一个完整 JSON 对象（**单行**，不含换行）。

- 帧间用**空行**分隔。

    

**心跳**：无业务输出时，每 **15 秒**发一次注释帧，防止网关空闲超时：



```Plain Text
: ping
```



**流内事件表**：



|`type`|字段|说明|
|---|---|---|
|`run-start`|`runId`, `conversationId`, `userMessageId`, `assistantMessageId`, `traceId`, `resume?`|**首帧，必须有**。前端靠它把流和消息绑定；`resume: true` 表示从 HITL 断点续流，前端保留已有气泡，不清空本地文本|
|`status`|`stage`: 见 `RunStage`|`thinking` / `searching_knowledge` / `drafting_graph` / `finalizing`|
|`text-delta`|`messageId`, `content`, `replace?`|增量文本，前端**追加**；`replace: true` 时用 `content` 整体替换本地气泡（仅缓冲失效合成重放使用）|
|`citation`|`sources[]`: `{fileId, fileName, snippet, score}`|知识库引用|
|`graph`|`graph`（`Graph`）, `replace: true`|**全量替换**，前端以最后一帧为准|
|`constraint-card`|`messageId`, `card`（`ConstraintCard`，含 `id`）|见 §6|
|`card-updated`|`cardId`, `status`, `answer`|可选，多卡片场景用|
|`interrupt`|`interruptId`, `kind`, `node`, `payload`, `expiresAt`|HITL 暂停帧；收到后关闭当前流，**不发送终态 `done`**；用户输入后 resume 同一 run|
|`usage`|`inputTokens`, `outputTokens`, `model`, `latencyMs`|仅观测|
|`title`|`conversationId`, `title`|AI 生成的标题，前端更新侧边栏|
|`error`|`code`, `message`, `retryable`|流内错误，**之后仍要发 ****`done`**** \+ ****`[DONE]`**|
|`done`|`assistantMessageId`, `finishReason`|终态结束发送，携带终态信息；HITL 暂停不发 `done`，改发 `interrupt`|



**结束标志**：



```Plain Text
data: {"type":"done","assistantMessageId":"msg_50","finishReason":"stop"}
data: [DONE]
```



> `done` 携带元信息，`[DONE]` 是终止哨兵（兼容前端既有解析逻辑）。收到任一即停止解析，并**重新拉一次 ****`GET /conversations/:id/messages`** 拿服务端权威数据。
>
> HITL 暂停是例外：只发 `interrupt`，不发 `done` / `[DONE]`；恢复后重新建立流。
> 
> 



**重连规则**：



|情况|行为|
|---|---|
|带有效 `Last-Event-ID` 重连|**优先**从该 id 的**下一帧**开始补发；补发完继续实时推送。不重复发送之前的帧|
|未带 `Last-Event-ID`，run 仍在运行|把缓冲内已有的帧全部补发，之后继续实时推送|
|run 已结束且在缓冲期内（10 分钟）|完整重放全部帧，然后发 `done` \+ `[DONE]` 并关闭|
|run 处于 `waiting_input`|从 `runs.metadata.interrupt` 重放 `interrupt` 帧后关闭；**不返回 409**，也不发 `done`|
|缓冲已失效（超期 / 进程重启）|**不返回 409**：按 `runId` 查 `runs` → `messages`，合成快照重放（见下）|
|`Last-Event-ID` 大于当前缓冲最新帧|服务重启 / 缓冲重建导致旧游标失效：忽略旧游标，按全量重放；不要因此返回 409|
|run 存在但关联的 assistant 消息已缺失|`409` / `RUN_NOT_RESUMABLE`，前端刷新消息列表|
|run 不存在 / 不属于当前用户|`404` / `RUN_NOT_FOUND`|

#### 事件缓冲与恢复（实现约束）

- **断线不终止运行**：`GET /runs/:runId/stream` 断开只关闭推送通道，不触发取消。Agent 继续推理，继续写事件缓冲和 `messages.content`。只有 `POST /runs/:runId/cancel`、运行超时、进程退出会终止 run。
- **数据库是权威存储**：生成过程中，服务端把累积文本按节流（约 1 秒或每 200 token，取先到者）写入 `messages.content`；终态再最终写入 `content`、`metadata.citations`、`metadata.usage`，并更新 `runs.status` / `finish_reason` / `usage` / `finished_at`。所以缓冲丢失后，`GET /messages` 仍能拿到已生成内容。
- **事件缓冲只用于逐帧重放**：MVP 单实例放进程内存（`Map<runId, { frames, lastId, expiresAt }>`），TTL 10 分钟，不引入 Redis。缓冲不是权威数据，进程重启即丢失。
- **缓冲失效的合成重放**：服务端按 `runs.assistant_message_id` 查 `messages`，依次发送：`run-start` → 一条全量 `text-delta`（`content` = `messages.content`，`replace: true`）→ 当前 `graph`（`conversations.current_draft_graph`）→ 终态 `done` + `[DONE]`。卡片、引用、用量从 `messages.metadata` / `runs` 补齐；逐 delta 和历史 `status` / `citation` 顺序不再重放。
- **缓冲生命周期**：run 进入终态后保留 10 分钟，到期清理；服务重启时清空。
- **全量补发时重置气泡**：未带 `Last-Event-ID` 或缓冲失效重放时，`run-start` 到达后前端应清空该 assistant 气泡的本地累积文本，再按后续帧重建，避免重复追加；合成重放的 `text-delta` 本身带 `replace: true`，可幂等覆盖。`resume: true` 的 `run-start` 是例外，前端保留已有气泡。



#### HITL 中断与恢复（interrupt / waiting_input）

1. 当 workflow 节点需要用户澄清、审批副作用操作或复核生成结果时，服务端把当前 `Interrupt` 写入 `runs.metadata`，把 `runs.status` 置为 `waiting_input`，发送 `interrupt` 帧后关闭当前 SSE 流；**不发送 `done`**。
2. `Interrupt` 至少包含 `interruptId`、`kind`（`clarification` / `approval` / `review`）、`node`、`payload`、`expiresAt`。`payload` 用 Zod 定义，前端按 `kind` 渲染卡片 / 审批 / 复核 UI。
3. 用户恢复：
   - 卡片作答走 `POST /api/v1/conversations/:conversationId/messages/:messageId/answer`；
   - 普通消息也可以作为 resume：服务端发现同会话有 `waiting_input` 的 run 时，继续该 run，不新建；
   - 恢复时用 `interruptId` 做幂等；已执行过的工具记录 ID，不重放有副作用的工具。
4. 恢复后重新建立 SSE 连接，`run-start` 使用同一个 `runId` / `assistantMessageId` 并带 `resume: true`；前端保留已有气泡，随后继续推送 `status` / `text-delta` / `graph` 等帧。
5. 等待超时（建议 24 小时）转 `canceled`；用户也可调用 `POST /api/v1/runs/:runId/cancel` 显式取消。
6. 如果客户端在 `waiting_input` 期间重连 `GET /stream`，服务端从 `runs.metadata.interrupt` 重放 `interrupt` 帧后关闭，不返回 `409`。

### 5.3 查询运行状态（轮询兜底）





```HTTP
GET /api/v1/runs/:runId
```



**响应 ****`200 OK`**：



```JSON
{
  "id": "run_9f1c",
  "conversationId": "cnv_1",
  "userMessageId": "msg_49",
  "assistantMessageId": "msg_50",
  "status": "succeeded",
  "finishReason": "stop",
  "createdAt": "2026-11-08T16:40:00+08:00",
  "finishedAt": "2026-11-08T16:40:09+08:00",
  "error": null
}
```



`error` 非空时：`{ ``"code": "INTERNAL_ERROR"``, "message": "..." }`



> **用途**：SSE 被企业代理缓冲/截断时的兜底。前端可退化为「1\.5s 轮询一次，`status` 变为终态后再拉消息列表」。
> 
> 



### 5\.4 取消生成



```HTTP
POST /api/v1/runs/:runId/cancel
```



**响应 ****`202 Accepted`**（取消是异步的，`status` 返回当前状态）：



```JSON
{ "runId": "run_9f1c", "status": "running" }
```



> 服务端尽快停止推理并保存**已生成的部分内容**（写入 `messages.content`，随后按终态做最终写入）；终态 `canceled` / `finishReason = canceled` 通过 SSE `done` 帧或 `GET /runs/:runId` 获得。
