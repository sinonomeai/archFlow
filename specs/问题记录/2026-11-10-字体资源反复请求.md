# 字体资源在页面返回时反复请求（2026-11-10）

> 2026-11-11 最终结论：项目改用系统字体，不再自托管中文字体。本文保留排查过程与中间方案，最终改动见文末。

## 现象

- 开发模式下登录进入工作台后，按浏览器返回，Network 面板会再次出现 4 个字体请求。
- 每个请求均为 `200`，且带有实际响应大小（单个约 80 KB）和平均约 150 ms 的响应时间，说明字体是真实走网络重新下载，而不是命中本地缓存。
- 切换到生产模式（`next build` + `next start`）验证时，同样观察到字体请求。

## 定位

1. 字体原先放在 `apps/web/public/fonts/`，通过 `globals.css` 中手写的 `@font-face` 以固定路径引用。
2. 实测该路径响应头为：

   ```http
   Cache-Control: public, max-age=0
   ETag: W/"82328-..."
   ```

   `max-age=0` 表示浏览器不能直接复用本地副本，每次都要回源确认。协商成功时返回 `304`；但缓存未命中或请求未带条件头时，服务端会返回 `200` 并重新传输完整文件。本次观察到的是后者。

3. Next.js 只对 `/_next/static/**` 下带内容 hash 的资源设置 `public, max-age=31536000, immutable`；`public/` 目录的文件名不随内容变化，Next 默认只给 `max-age=0`。
4. 开发模式下 HTML 为 `Cache-Control: no-store`，且存在 HMR 的长连接，页面无法进入 bfcache；因此按返回等同于重新打开文档，字体重新走一遍缓存协商。
5. 补充：修复前观察到的是带响应大小和耗时的真实下载；修复后再复查时，`200` 不能直接等同于“重新下载”。以下情况都会显示 `200`：
   - `200 (from memory cache)` / `200 (from disk cache)`，Size 为 `0 B`，实际未联网；
   - DevTools 勾选 `Disable cache`，强制所有请求真实发出；

## 决策

改用 `next/font/local` 自托管字体，不再手工维护 `@font-face` 和 `public/` 下的字体文件。

理由：

- 构建时自动为字体文件生成内容 hash，输出到 `/_next/static/media/`；
- 自动附带一年期 `immutable` 缓存，浏览器首次获取后不再回源；
- 字体更新时 hash 自动变化，不存在旧缓存命中问题；
- 同时获得 Next 的字体预加载、fallback 度量与 `display` 控制。

说明：内容 hash 不是可选项，而是 `next/font` 的固定输出；它是让“固定一年缓存”能够安全使用的前提。备选方案是继续使用 `public/fonts` + 手写 `@font-face`，并在 `next.config.ts` 为 `/fonts/:path*` 配置长缓存。该方案能保留明文文件名，但换字体时必须手动改名，否则旧缓存不会失效。本项目优先选择自动化，接受不可读的哈希文件名。

## 实施

- 新增 `apps/web/app/fonts.ts`：用 `localFont` 声明 400 / 500 / 600 / 700 四个字重，暴露 `--font-harmony-sans`。
- `apps/web/app/layout.tsx`：`<html>` 的 className 追加 `harmonySans.variable`。
- `apps/web/app/globals.css`：删除四段手写 `@font-face`，`--font-sans` 改为 `var(--font-harmony-sans), ...`。
- 字体文件从 `apps/web/public/fonts/` 移至 `apps/web/fonts/`，不再作为公开静态资源直接暴露。
- 字体移走后 `apps/web/public/` 已无内容，目录一并删除；后续仅在有固定 URL 需求（`robots.txt`、验证文件、下载文件等）时重建。

### 2026-11-11 补充：去掉未使用的 700 字重

`next/font` 默认会 preload 所有声明的字重。原实现声明了 400 / 500 / 600 / 700 四个字重，但源码中没有 `font-bold`、`<strong>` 或 `font-weight:700` 的使用；700 仍会被预加载，首次加载多下载约 528KB。

现已从 `apps/web/app/fonts.ts` 移除 700 声明，只保留 400 / 500 / 600。字体总量从约 2.1MB 降到约 1.6MB；Bold 文件当时仍保留在 `apps/web/fonts/`，需要时再加回声明（后续最终方案已删除整个字体目录）。`preload` 仍保持默认开启，避免三档字重出现明显的字体闪烁。

## 验证

- `pnpm build` 通过。
- 生产模式下字体地址形如 `/_next/static/media/172c489657bd7532-s.p.woff2`，响应头为：

  ```http
  Cache-Control: public, max-age=31536000, immutable
  ```

- 生产模式按返回不再触发字体请求；开发模式仍可能看到 `0 B` 的 `(disk cache)` 记录，这是 bfcache 被禁用后的缓存查询，不是网络下载。

## 经验

- `public/` 只适合“URL 必须固定、内容原样输出、不经过构建处理”的文件（`robots.txt`、验证文件、下载文件、外部引用的图片等）。需要构建处理或长期缓存的前端资源应放源码目录，交给 `next/font`、`next/image` 或 `/_next/static` 的指纹化产物。
- 放进 `public/` 不会自动获得缓存：Next 对其默认返回 `max-age=0`，需要长缓存时必须自己配 `headers` 或交给 CDN。
- 排查“是否真的重新请求”时，看 DevTools 的 Size 列和 `(disk cache)` / `(memory cache)` 标记，而不是只看状态码 `200`。
- 开发模式不能进 bfcache 是预期行为；用生产模式验证返回/缓存行为才有意义。

## 附：浏览器如何判断资源是否需要缓存

浏览器的 HTTP 缓存分两层：**强缓存（freshness）**决定“能不能直接用本地副本”，**协商缓存（validation）**决定“本地副本还能不能用”。

### 一次请求的判断流程

1. **查本地缓存**：这个 URL 有没有存过？请求方法是不是 `GET` / `HEAD`？`Vary` 指定的请求头是否匹配？都不满足就直接走网络。
2. **算新鲜度**：根据响应里的 `Cache-Control: max-age=N` 或 `Expires`，算出“新鲜期”；再结合 `Date`、`Age` 判断现在是否还在期内。
3. **还在期内 → 强缓存命中**：不发任何网络请求，直接用本地文件。DevTools 显示 `200 (from memory cache)` 或 `200 (from disk cache)`，Size 为 `0 B`。
4. **过期了 → 协商缓存**：带条件请求头回源：
   - `If-None-Match: <ETag>`（对应响应头 `ETag`）；
   - `If-Modified-Since: <Last-Modified>`（对应响应头 `Last-Modified`）。
5. **服务器判断**：
   - 内容没变 → `304 Not Modified`，不传响应体，浏览器继续用本地副本，同时用 304 里的新响应头更新新鲜度；
   - 内容变了或无法判断 → `200`，传完整响应体，替换本地副本。

### 相关响应头

**`Cache-Control`（优先级最高）**

| 指令 | 含义 |
| --- | --- |
| `max-age=N` | 响应在 N 秒内是新鲜的，可以直接用 |
| `s-maxage=N` | 只对 CDN / 共享缓存生效，优先级高于 `max-age` |
| `no-cache` | **可以存**，但每次使用前都必须回源验证（不是“不缓存”） |
| `no-store` | 完全不存，连本地副本都不留（敏感数据用） |
| `must-revalidate` | 过期后必须验证，不能拿过期副本凑合 |
| `immutable` | 在新鲜期内，即使用户刷新也不回源验证 |
| `public` / `private` | 是否允许 CDN 等共享缓存存储 |

**`Expires`**

HTTP/1.0 的绝对时间写法，例如 `Expires: Wed, 11 Nov 2026 00:00:00 GMT`。它和 `Cache-Control: max-age` 同时出现时，**`max-age` 优先**。因为依赖客户端时钟，现在基本只作为兼容兜底。

**`ETag`**

内容的指纹，例如 `ETag: W/"82328-1a1c12fce0f"`。浏览器下次请求时通过 `If-None-Match` 带回去。

- 强 ETag：内容逐字节一致才相同；
- 弱 ETag（`W/` 前缀）：只保证语义等价，不保证字节一致。

**`Last-Modified`**

资源的最后修改时间，浏览器通过 `If-Modified-Since` 带回去。它是**秒级**精度，且同一秒内多次修改无法区分，所以校验能力弱于 `ETag`；两者同时存在时，服务器通常优先看 `ETag`。

**`Age`**

这个响应在共享缓存（CDN）里已经待了多少秒，用来配合 `max-age` 计算剩余新鲜期。

### 常见组合与结果

| 响应头 | 浏览器行为 | DevTools 表现 |
| --- | --- | --- |
| `max-age=31536000, immutable` | 一年内直接用，不验证 | `200 (disk/memory cache)`，0 B |
| `max-age=0` + `ETag` | 每次都带 `If-None-Match` 验证 | 未变 → `304`；变了/未带条件头 → `200` + 实际大小 |
| `no-cache` + `ETag` | 每次都必须验证 | `304` 或 `200` |
| `no-store` | 不存，每次完整请求 | `200` + 实际大小 |

### 和 bfcache 的区别

HTTP 缓存存的是**单个资源**；bfcache 存的是**整个页面的内存快照**，包括 DOM、JS 状态和滚动位置。按浏览器返回时：

- 页面能从 bfcache 恢复 → 什么都不请求，也不解析 CSS；
- 不能从 bfcache 恢复（例如 dev 模式下 HTML `no-store`、HMR 长连接）→ 重新打开文档，CSS 重新解析，字体再按上面的 HTTP 缓存规则判断一次。

所以“返回时字体又出现请求”可能只是 HTTP 缓存层面的校验，也可能是页面根本没进 bfcache，需要分开看。

### 回到本次问题

- 原方案：`public/fonts` + `Cache-Control: public, max-age=0` + `ETag` → 本地有副本，但每次都要验证；当缓存条目不可用或请求没带条件头时，服务器回 `200` 并重传完整文件。
- 中间方案：`next/font/local` 产物 + `max-age=31536000, immutable` → 一年内视为新鲜，直接命中本地缓存，连验证请求都不发。
- 判断是否真的重新下载，永远以 DevTools 的 Size 列和 `(disk cache)` / `(memory cache)` 标记为准，不能只看状态码 `200`。

---

## 2026-11-11 最终方案：改用系统字体

`next/font/local` 解决了“重复请求”，但没有解决“首次加载要下 1.6MB 中文字体”的问题。MVP 阶段重新评估后，决定不再自托管中文字体：

- 400 / 500 / 600 三个字重约 1.6MB，首次打开成本高于品牌收益；
- 中文系统字体（苹方、微软雅黑、Noto Sans CJK）在排版上足够，差别主要是字形风格和字重匹配；
- 删除 `apps/web/app/fonts.ts` 与 `apps/web/fonts/`，`--font-sans` 改为系统字体栈；
- 字体请求归零，仓库/部署体积减少约 2.1MB。

后续如果确实需要统一品牌字体，再按“只保留实际使用的 1~2 个字重”重新引入，不要默认声明全部字重。

## 2026-11-13 恢复：HarmonyOS Sans 400 / 500 / 600

产品侧确认仍希望保留品牌字体，已从 Git 历史恢复 400 / 500 / 600 三个字重（约 1.6MB），继续使用 `next/font/local`：

- `apps/web/fonts/`：恢复 Regular / Medium / Semibold 三个 WOFF2；

如果后续再次关注首屏体积，优先做字符子集化（当前约 4500 字），而不是直接删除字体。
